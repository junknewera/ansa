# Парный A/B с контрольной выборкой

Добавьте в обычный манифест два варианта с разными `id`. Этот пример сравнивает два файла пользовательских инструкций.

```json
"comparison": {"left": "baseline", "right": "candidate", "factor": "guidance"}
```

Остальные поля вариантов, включая маршрут, профиль авторизации, mode и effort, должны совпадать. Для `binary`, `mcp_config` и `guidance` сравниваются SHA-256 содержимого. Другие допустимые факторы — `model`, `mode`, `effort`, `roles`. При сравнении ревизий бинарника зафиксируйте ревизии и опции сборки в описании эксперимента. Стенд проверяет хеши бинарников; смысловую разницу их исходников устанавливает автор.

Каждая задача получает поля `category` (например, `retrieval`), `family` (один идентификатор для вариантов одного сюжета), `split` (`development` или `holdout`) и, для исполнимых задач, `oracle_fixture`. Полностью неподдерживаемая задача остаётся в расписании со статусом `unsupported`. Родственные задачи должны лежать в одной выборке. В каждой выборке нужна хотя бы одна исполнимая задача для обоих вариантов. Запуск по умолчанию использует development. Параметр `--split holdout` явно выбирает контрольные задачи.

## Проверка оценщика

`oracle_fixture` — исполняемый файл за пределами входного workspace. Перед обращением к модели стенд дважды вызывает его с аргументами `pass|fail WORKSPACE ANSWER_JSON`. Fixture должна подготовить в пустом каталоге нужное состояние, записать ответ по указанному пути и выйти с кодом 0. Внешние входы fixture и оценщика перечислите в `verifier_inputs`. Затем тот же `verifier WORKSPACE ANSWER_JSON`, который оценивает сессию, должен вернуть 0 для правильного результата и 1 для заведомо неправильного. Для каждого контроля суммарное время подготовки и проверки ограничено `verifier_seconds`. Логи и коды возврата успешной калибровки хранятся в `controls/<task>/`. Расхождение останавливает запуск до обращения к модели.

Минимальный пример исполняемых fixture и оценщика, а также работающих манифестов и результатов двух вариантов есть в `test_comparison.py`. Команда запускает пример локально с синтетическими исходами сессий.

```sh
python -B benchmarks/test_comparison.py
```

## Запуск и чтение результатов

Сохраните планы обеих выборок *до* первого прогона. Они включают задачи, расписание, SHA-256 программ, подготовленных данных и оценщиков, параметры моделей и бюджеты.

```sh
python -B benchmarks/bench.py manifest.json > dev-plan.json
python -B benchmarks/bench.py manifest.json --split holdout > holdout-plan.json
python -B benchmarks/bench.py manifest.json --frozen-plan dev-plan.json --output runs-dev --live
python -B benchmarks/bench.py manifest.json --split holdout --frozen-plan holdout-plan.json --output runs-holdout --live
```

Для правки промпта планирования, ревью или свёртки добавьте `"stage": "planner"`, `"reviewer"` или `"compaction"` внутрь `comparison`. При планировании стенд проверяет запрос принятого ответа с назначением `orchestration_plan`. Для ревью нужен ответ в дочернем журнале ревью по замороженному кандидату или с записанным хешем review skill. Для свёртки нужен записанный переход `compacted`. В `usage.stages` перечислены журналы, подтвердившие стадию. Если стадия пропущена хотя бы в одной половине оценённой пары, результат пары — `stage_missing`, код завершения запуска — 1.

В `report.json` результат каждой пары привязан к задаче и повтору. `left_only` и `right_only` означают победу указанного варианта. Ошибки стенда, неподдерживаемые задачи и пропущенные стадии учитываются отдельно от побед. Разбивка по типу задач находится в `comparison.by_category`, покрытие режимов — в `comparison.coverage`. Метрики времени, ответов модели, инструментов и токенов даны по вариантам. Рядом с каждой суммой указано число попыток, передавших значение. Расход токенов без отчётности провайдера остаётся неизвестным.
