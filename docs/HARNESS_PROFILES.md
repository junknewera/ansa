# Профили проекта

Профиль хранит инструкции проекта, короткие факты с источниками и процедуры, которые агент загружает через `list_skills` и `read_skill`. Новый разговор получает активную ревизию проекта. Продолжение и ответвление закреплены за ревизией исходного разговора. Инструкции профиля подчиняются пользовательским указаниям, AGENTS.md и правам инструментов.

## Начальный профиль и кандидат

Все команды принимают один и тот же канонический каталог проекта. `baseline` однократно публикует начальный профиль. Пустой начальный профиль позволяет сохранить одинаковый набор инструментов при сравнении.

```sh
printf '%s\n' '{"version":1,"guidance":"","skills":[],"memory":[]}' |
  ansa --harness baseline --cwd "$PROJECT"
ansa --harness status --cwd "$PROJECT"
```

Полный входной профиль может содержать такие данные.

```json
{
  "version": 1,
  "prompt_policy": "handoff-v1",
  "guidance": "Проверяй результат сборки по итоговому артефакту.",
  "skills": [
    {"name": "verify", "trigger": "проверка сборки", "body": "Собери проект и проверь итоговый артефакт."}
  ],
  "memory": [
    {"fact": "Тесты используют синтетические фикстуры.", "source": "tests/README.md", "applies_when": "локальная приёмка"}
  ]
}
```

Необязательное поле `prompt_policy` выбирает текст для свёртки. Значение по умолчанию `legacy-v1` сохраняет исходный промпт. Вариант `handoff-v1` просит указать, какие задачи завершены, что проверено и какие эффекты остались неизвестными. Возобновлённая сессия использует сохранённый вариант.

Зафиксируй план, пока исходный профиль активен, затем передай один кандидат.

```sh
ansa --harness freeze --cwd "$PROJECT" "$BASELINE_REVISION" < plan.json
ansa --harness stage --cwd "$PROJECT" "$FREEZE_ID" < candidate.json
ansa --harness status --cwd "$PROJECT"
```

Из ответа `freeze` возьми `freeze`. Из ответа `stage` возьми `proposal` и `candidate`. `stage` не меняет активную ревизию и не запускает модель. Повтор с тем же кандидатом возвращает прежний идентификатор.

## План и запуск сравнения

`plan.json` содержит `version: 1`, `repetitions` от 2 до 4, объекты `development` и `holdout`, а также бюджеты `per_trial` и `total`. Совокупно план ограничен 32 запусками, включая оба варианта и все повторы.

Каждый объект задач содержит записи с уникальными именами. В записи нужны поля `prompt_sha256` (SHA-256 точного UTF-8 текста отправленного задания), `inputs` (имя файла → SHA-256 исходных байт) и `checks` (имя артефакта → SHA-256 ожидаемых байт). В каждом наборе нужен хотя бы один вход и одна проверка. Используй базовые имена файлов из ASCII букв, цифр, точки, дефиса и подчёркивания, начиная с буквы или цифры. Prompt и имя задачи уникальны среди development и holdout. Для простых задач достаточно одного проверяемого файла. Замораживай контрольные задания и критерии до подготовки кандидата и держи эталоны отдельно от среды исполнения.

Оба бюджета содержат целочисленные `calls`, `tools`, `compactions` и `estimated_input_tokens`. Это границы наблюдений по сохранённому журналу. Провайдерские токены учитываются отдельно, когда они известны. Ограничения фактического запуска выставляет оператор, включая лимит времени и внешнего расхода. `evaluate` работает офлайн и новых обращений к провайдеру не делает.

Каждому запуску нужна новая сессия. Для обоих вариантов используй один и тот же каталог проекта с восстановленными исходными данными, одинаковые модель, учётную запись, effort, настройки и набор инструментов. `--harness-trial` выбирает вариант из замороженного сравнения, записывает его идентификатор и вариант в журнал и оставляет активный профиль прежним.

```sh
ansa --harness-trial "${FREEZE_ID}:baseline" --cwd "$PROJECT" "$PROMPT"
ansa --harness-trial "${FREEZE_ID}:candidate" --cwd "$PROJECT" "$PROMPT"
```

Каждая команда создаёт журнал в каталоге сессии. Перед следующим запуском оператор сохраняет его и файлы этого запуска в отдельный закрытый каталог. Собери все пары под одним абсолютным каталогом evidence. Например, для первого запуска задачи `build` со старым профилем структура такая.

```text
EVIDENCE/build/1/baseline/session/
EVIDENCE/build/1/baseline/inputs/<input-name>
EVIDENCE/build/1/baseline/artifacts/<artifact-name>
EVIDENCE/build/1/candidate/session/
EVIDENCE/build/1/candidate/inputs/<input-name>
EVIDENCE/build/1/candidate/artifacts/<artifact-name>
```

`session/` содержит канонический журнал ANSA. Каталог evidence с собранными парами и эталонами должен контролироваться оператором или отдельной средой оценки. Shell в ANSA работает с правами пользователя, поэтому разделение проверок и исполнителя требует внешней изоляции. Отчёт из рабочего каталога агента не служит источником решения.

## Решение и откат

```sh
ansa --harness evaluate --cwd "$PROJECT" "$PROPOSAL_ID" "$EVIDENCE"
ansa --harness adopt --cwd "$PROJECT" "$PROPOSAL_ID"
ansa --harness status --cwd "$PROJECT"
ansa --harness rollback --cwd "$PROJECT" "$ACTIVE_ACTIVATION_ID" "$TARGET_ACTIVATION_ID"
```

`evaluate` пересчитывает контрольные суммы по файлам, проверяет журналы и сохраняет результат один раз. Для статуса `eligible` нужны завершённые запуски в рамках бюджетов, отсутствие регрессий в каждой паре и хотя бы одна holdout-задача, которую кандидат стабильно проходит во всех повторах после неуспеха baseline. В одном сравнении можно оценить изменение одной категории профиля - guidance, skills, memory или prompt policy. Смешанный кандидат доступен для пробных запусков, а его оценка получает `confounded: true` и `NO_ENTRY`. Остальные полные сравнения без доказанного улучшения также дают `NO_ENTRY`. Неполные или противоречивые исходные данные дают диагностический ответ.

Только явный `adopt` активирует подходящего кандидата. Перед записью решения он повторяет проверку сохранённого архива. Архив должен оставаться доступным по исходному пути с теми же журналами и файлами. Если активная ревизия сменилась после заморозки, решение требует нового сравнения. `status` показывает историю и идентификаторы активаций. `rollback` добавляет новую активацию, указывающую на содержимое выбранной исторической ревизии. Повтор успешно сохранённого решения возвращает прежнюю активацию. Уже открытые разговоры сохраняют выбранные ранее ревизии.

Для воспроизводимой офлайн-проверки выполните `nix develop -c python -B tests/harness_profile_eval.py --binary /absolute/path/to/ansa --output /absolute/path/to/new-directory`. Драйвер создаёт восемь отдельных сессий в своём временном проекте, сбрасывает входной файл перед каждой попыткой и оценивает вывод обеих версий по заранее зафиксированным критериям. При одинаковом результате активной остаётся исходная версия. Для оценки качества свёртки в длинном диалоге нужны отдельные многоходовые задания.
